# Activation functions on the FPGA — LeakyReLU, SiLU, GELU

**Status (2026-10-06):** step 1 done — VectorOPKernel computes LeakyReLU,
SiLU, GELU (erf) and GELU (tanh) in hardware, as ops and as fused
activations after any op; bit-exact against the C++ model on every Q8.8
input, verified at 300 MHz out of context.  Step 2 done — the scheduler
maps ONNX `Gelu`, `LeakyRelu` and `x · Sigmoid(x)` onto it behind a
platform capability (§5).  Step 3 done — bitstream `6436623029f7`
(250 MHz, WNS +0.061 ns) is in production: 156 / 156 models, every
library gate bit-exact, BERT 541 → 525 ms with its GELUs on the FPGA (§6).

## 1. Why

The 250 MHz design ([FMAX_250_PLAN](FMAX_250_PLAN.md), bitstream
`986cef4866a0`) uses 47.8 % of the LUTs, 103 of 144 BRAM36, 48 of 64 URAM
and 688 of 1 248 DSPs — room for the activations that today run on the A53:
BERT's GELU (`GeluNode`, a host op over the whole FFN tensor), Piper's
LeakyReLU (inside `TtsPrep`), the Llama decoders' SiLU (`LlmSiluMul`).  The
first step puts them in VectorOPKernel, the simplest kernel: as unary ops,
and through `act` after an add / sub / mul / div, so a bias Add → GELU is
one pass over the data.  The same unit can later sit in ConvKernel's or
MatmulKernel's output path (§7).

## 2. Interface

| | codes | notes |
|---|---|---|
| ops (unary, no gmem1 traffic) | 6 `OP_LEAKY_RELU`, 7 `OP_SILU`, 8 `OP_GELU`, 9 `OP_GELU_TANH` | the activation of `a`; the `act` register is not applied after them |
| acts (after any op) | 3 `ACT_LEAKY_RELU`, 4 `ACT_SILU`, 5 `ACT_GELU`, 6 `ACT_GELU_TANH` | 1 / 2 stay ReLU / ReLU6; codes ≥ 7 none |
| register `alpha` (`0x64`, appended last) | LeakyReLU's slope `alpha[15:0] / 65536` | 0 ≤ slope < 1 (ONNX's 0.01 → 655, 0.1 → 6554); bits 31:16 stored, ignored |

`VectorOP.h`: `Op`, `Act`, `job_act(op, act)`; older op / act codes are
unchanged, and op codes ≥ 10 still pass `a` through.  An IP without the unit
(every bitstream so far) passes ops 6–9 through as identity and ignores acts
3–6 — so the scheduler must know which bitstream it targets before it emits
them (§5).

## 3. Numerics

Every activation gives the exact function of the Q8.8 input, rounded to the
nearest Q8.8 value, ties to even — the write-back rounding of the host ops
(`host_nodes.py`): `GELU(x) = x Φ(x)`, `GELU_tanh(x) = x/2 (1 + tanh(√(2/π)
(x + 0.044715 x³)))`, `SiLU(x) = x / (1 + e⁻ˣ)`, LeakyReLU `x ≥ 0 ? x :
x · alpha / 2¹⁶` (the product is exact; ties occur, e.g. −1 LSB · ½).

- **Double is exact here.**  For each of the 65 536 inputs the nearest
  rounding tie is at least 1.6 × 10⁻⁵ LSB away (GELU at x = −539/256; SiLU
  3.6 × 10⁻⁴, GELU tanh 2.1 × 10⁻⁴), and IEEE double with libm's `exp` /
  `erf` / `tanh` rounds every input as 40-digit mpmath does.  So the C++
  model (`act_fn` in `VectorOP.cpp`), the ROM generator and any host
  implementation in double agree bit for bit.
- **float32 constants change nothing.**  BERT's fused GELU carries its
  constants as float32 (`x / 1.4142135` or `x · 0.70710677`; tanh form
  `0.044715f`, `0.7978846f`); computed in double with those constants it
  gives the same Q8.8 result as the exact constants on all 65 536 inputs —
  the kernel's GELU is bit-identical to today's host `GeluNode`.  (The erf
  and tanh forms differ from each other on 108 inputs, by 1 LSB: both are
  kept.)
- **The table identity.**  SiLU and both GELUs are `x · F(x)` with
  `F(−x) = 1 − F(x)`, so `f(x) = max(x, 0) + f(−|x|)`; `max(x, 0)` is a whole
  number of LSBs, so the rounded values obey it too (checked on every input).
  `−round(256 · f(−t/256))` lies in 0…71 (7 bits) and is 0 beyond
  t = 2 140 (SiLU, |x| ≥ 8.36), 828 (GELU, 3.24), 815 (GELU tanh, 3.19):
  3 786 entries in all, one 4 096 × 7 ROM.

## 4. Implementation and results (step 1, VectorOPKernel)

**RTL** ([VECTOROP_RTL_KERNEL](../kernels/VECTOROP_RTL_KERNEL.md) §1–2, §6):
`vo_act` sits after the ALU and DIV paths merge, a fixed 7-cycle pipeline
on the 8-lane words — per lane `|x|`, the ROM address and past-the-table
flag, a two-port block ROM (`vo_act_rom`, one BRAM36 per two lanes, output
register), `max(x, 0) − m`; LeakyReLU in one DSP48E2 per lane (A / B
registers, M, P) with the round-to-nearest-even of the 33-bit product in
fabric.  `vo_compute` counts the words in flight from the take to its
output FIFO (now 32 words) in one counter; the job's activation is decoded
in two registered steps.  `rtl/vo_act_rom.sv` is generated by
`kernels/vectorop_rtl/scripts/gen_act_rom.py` (`--exact`: mpmath check of
every entry; ctest `VectorOpRtlActRom`: the file is current).

## 5. Step 2 — the scheduler (2026-10-06)

- **Gate:** `platforms/kv260.json` `kernels.vectorop.activations` (true:
  the KV260's bitstream has the unit), `AXI_VECTOROP_ACTIVATIONS=0` / `1`
  overrides it (`src/_vectorop_hw_config.py`).  Only `ap_fixed<16,8>`
  tensors without a power-of-two exponent or host memory qualify.
- **Mapping** (`src/vectorop_act.py`): `Gelu` (native, or a fused GELU
  pattern with the graph's constants) → `OP_GELU` / `OP_GELU_TANH` when its
  Q8.8 table equals the kernel's on all 65 536 inputs, else the host op;
  `LeakyRelu` → `OP_LEAKY_RELU` with `round(alpha · 2¹⁶)`; `Mul(x,
  Sigmoid(x))` → `Silu` (`fusion.py`, only with the unit) → `OP_SILU`.
  `_fuse_activations` folds all four into a producing Add / Sub / Mul /
  Div (`act`, the slope carried), never into an activation op.
- **Simulator:** the op result truncated as for every op, then the
  activation in double rounded to nearest-even (`vectorop_act.apply`) —
  the kernel's semantics; the software VectorOP of `test/host_emu.py`
  implements the same in C.
- **Code:** `run_op_act(…, act, alpha)`; a program that uses the unit
  writes `alpha` plainly and checks at `inference_init()` that the IP has
  the register (writes 0x5A5A, reads it back — an older IP reads 0 and
  would pass ops 6–9 through); every other program writes `alpha = 0`
  where the driver has it (`#ifdef XVECTOROPKERNEL_CTRL_ADDR_ALPHA_DATA`).
- **Effect on the shipped models:** BERT-SQuAD's 12 GELUs (tanh form,
  float32 constants) leave the host and run fused into the FFN bias Adds
  (`ADD` + act `GELU_TANH`) — bit-identical (`test_bert_base`: the
  study's SQuAD example bit for bit, the C emulation of the whole model);
  the other shipped models have no `Gelu` / `LeakyRelu` / SiLU node.
- **Tests:** `test/test_activations.py` (19: the scheduler's tables equal
  the RTL's generated ROM on every input, the mapping and fusion rules, the
  gate, the emitted code, simulation on every input, the eight models of
  `test/gen_activation_models.py` compiled against the software kernels);
  BERT-tiny / BERT-base on both sides of the gate; the host-GELU tests pin
  the gate off.  The eight models join the on-board suite (156 models):
  `act_gelu`, `act_gelu_tanh`, `act_leaky_relu`, `act_silu` take a
  [1, 65536] input, which the harness's ramp fill makes every Q8.8 value.

## 7. Next steps

1. **More GELU sites.**  BERT's GELUs were already bit-identical on the host;
   the gain (16 ms per inference) is the host pass they no longer need.
   SmolVLM's vision encoder (`VitGelu`) and Piper's `TtsPrep` LeakyReLU run on
   tensors with power-of-two exponents: LeakyReLU is scale-free
   (`f(2ᵉx) = 2ᵉ f(x)`) and could move as is; GELU / SiLU need a shift into
   Q8.8 before the table or a table per exponent.  Done in
   [OFFLOAD_PLAN](OFFLOAD_PLAN.md): SmolVLM's GELU moved (the shift, two
   VectorOP passes); Piper's LeakyReLU stayed in `TtsPrep` (no host pass to
   save), its decoder's residual sums moved instead.
2. **Other kernels.**  `vo_act` / `vo_act_rom` are self-contained (lanes,
   job constants, fixed latency): ConvKernel's drain and MatmulKernel's
   writer could apply an activation before the write — Conv → LeakyReLU in
   Piper's HiFi-GAN, MatMul → GELU in BERT (today the GELU rides on the bias
   Add, one extra pass) — saving the separate pass.
3. **The engine cost model at 250 MHz** (FMAX_250_PLAN's open item) — the
   performance model's families stay loose until it is refitted.
